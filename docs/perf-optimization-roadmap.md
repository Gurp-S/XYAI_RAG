# XYAI 检索链路性能优化路线图

> 背景：JMeter 100 并发压测（r100），932 次检索请求 0 错误，P50 8.3s / P95 8.85s / P99 9.38s / max 10.57s。
> 结论先行：**P99 高不是失控，是排队**——虚拟线程把 100 并发全额透传给两个串行下游，排队堆在中位数上（P50 也有 8.3s，说明不是长尾抖动，是系统性容量问题）。

## 一、瓶颈定位（已核实代码）

| # | 瓶颈点 | 证据 | 影响 |
|---|--------|------|------|
| 1 | Rerank 走本地 Ollama 单点 | `commonUtils/OllamaRerankerService`，`localhost:11434` | 单 GPU 本地推理串行消化请求，100 并发下每请求排队数秒 |
| 2 | 查询重写是关键路径上的同步 LLM 调用 | `rag/rewrite/QueryRewriter.java:126` `chatModel.call(prompt)` 阻塞调用 | 每请求 +1 次 LLM RTT，受 dashscope 账号限流放大 |
| 3 | 执行器名义隔离、实际同源 | `ThreadPoolConfig`：mcp/search/intent/graph/milvus/chat 全部返回同一个 `ioBoundExecutor`（虚拟线程） | 并发不被池大小挡住 → 全额打到下游（这本身没错，但下游必须有对应容量与限流） |
| 4 | 无查询级缓存 | 重写结果 / embedding / 检索结果均未缓存 | 相同与相似查询重复付出全链路成本 |

## 二、先做定位，再动手（半天）

系统自带 `@RagTraceNode` 节点级追踪——压测窗口的 `trace_record` 就是现成的瓶颈报告：

1. 拉取压测时段各节点的 P50 / P99 耗时，按贡献排序；
2. 预期排序：Rerank > LLM 重写 > 向量召回 > 图谱社区 > BM25/过滤；
3. 顺带测**并发=1 基线**：单请求 P50（估 2–4s）。基线与 9.38s 的差值 = 排队成本，是所有优化的对照基准。

## 三、优化项（按 ROI 排序）

### P0-1 Rerank 卸载本地单点（预期最大收益）
- 本地 Ollama rerank → 托管 rerank API（阿里云 Bailian gte-rerank 系列）或自建 GPU 推理服务（TEI / Xinference 部署 bge-reranker-v2-m3，支持 batch）；
- 只送 Top-K 进 rerank（候选截断，如 50 → 20）；
- 提供"低延迟档"：高峰/压测模式跳过 rerank，用 BM25 + 向量分数融合保底。

### P0-2 查询重写去关键路径
- 规则重写命中即走（已有二级设计）→ 高峰档强制规则档；
- LLM 重写换小快模型（qwen-turbo / flash 档）+ Resilience4j Bulkhead 限并发；
- **重写结果缓存**：query 归一化（去空格/标点/大小写）后 Redis 缓存，TTL 1h。

### P1 查询级缓存三层
- embedding 缓存（归一化 query → 向量）；
- 检索结果短 TTL 缓存（同 query 30s 内直返，压测同 query 场景收益极大）；
- 意图缓存已有 ✓ 保持。

### P1-2 下游限流 + 快速降级（把排队变成决策）
- 对 dashscope / rerank 服务各设 Bulkhead 信号量（容量 = 下游真实并发额度）；
- 拿不到额度的请求**立即走降级链**（跳过 rerank → 规则重写 → 直接向量检索），而不是在队列里排 9 秒；
- 效果：P99 从"重链路排队延迟"变成"轻量链路延迟"，同时 0 错误保持。

### P2 检索参数与数据面
- Milvus ivf_flat `nprobe` / `topK` 调参（精度-延迟换算表压测确定）；
- 按用户/租户做 partition，缩小 ACL 过滤扫描面；
- Neo4j 社区查询加深度限制与超时。

### P3 容量路线
- 应用无状态（会话已在 Redis）→ 多副本 + LB，吞吐近线性扩展；
- 本地模型全部外移（vLLM / 托管 API），应用节点只做编排。

## 四、量化目标

| 阶段 | 100 并发 P99 | 说明 |
|------|-------------|------|
| 现状 | 9.38s | 0 错误，超时兜底 |
| P0 两项完成 | 3–4s | Rerank 卸载 + 重写缓存/降级 |
| +P1 缓存 + 多副本 | <2s | 缓存命中率决定上限 |

每步完成后**重跑同一 JMeter 脚本**出对照数字（同 r100 配置），没有对照数字不算优化完成。

## 五、简历/面试话术升级路径

- 现在的防御表述：「100 并发 0 错误，P99 9.38s 被单通道 10s 超时设计兜住——尾部有界、无级联失败」；
- 优化后的进攻表述：「压测定位 Rerank 与 LLM 重写为关键路径瓶颈（节点级追踪），本地推理卸载 + 重写缓存 + Bulkhead 快速降级三步，100 并发 P99 9.4s → X.Xs（−Y%），全程 0 错误」；
- 面试一句话：「9.38s 不是失控延迟，是设计上限内的排队延迟；节点级追踪证明瓶颈在下游单点不在编排路径，我的优化方案是把排队延迟换成降级决策」。
