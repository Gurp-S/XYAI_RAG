# RAG 项目 12 周路线图

> 目标：把当前已完成的 RAG 核心能力，升级为可高可用、可观测、可维护、可交付的企业级项目。
>
> 进度状态统一使用：`ToDo / Doing / Done`
>
> 每天结束前更新一次状态；若遇到阻塞，标记为 `Doing` 或补充阻塞原因，不要放置不更新。

## 1. 项目目标

- 稳定支撑知识入库、检索、问答、历史追踪等核心流程
- 提升安全性、可观测性、可恢复性和交付能力
- 让系统具备后续多人协作、灰度发布、容量扩展的基础

## 2. 非目标

- 不在本阶段追求过度复杂的微服务拆分
- 不优先堆叠无业务价值的炫技特性
- 不引入难以维护的重型平台化方案

## 3. 企业级完善方向

1. 安全与配置治理
2. 认证授权与接口边界
3. 可观测性与审计留痕
4. 稳定性与限流保护
5. RAG 入库治理与数据质量
6. 检索质量与评估闭环
7. 交付自动化与回滚能力
8. 备份恢复与容灾演练

## 4. 12 周路线图

| 周次 | 主题 | 目标 | 关键交付物 | 验收标准 |
|---|---|---|---|---|
| W1 | 安全基线与配置治理 | 清理明文配置，建立环境分层 | 配置外置方案、密钥管理约定 | 敏感信息不入库，环境切换可用 |
| W2 | 认证授权与接口边界 | 建立用户身份和权限边界 | 登录/鉴权方案、接口权限清单 | 关键接口受保护，未授权访问被拦截 |
| W3 | 可观测性基线 | 统一日志、指标、链路标识 | `traceId`/`requestId`、健康检查、指标暴露 | 出问题能快速定位到请求 |
| W4 | 稳定性保护 | 提升抗压与降级能力 | 超时、重试、限流、熔断、隔离 | 高峰期不出现级联故障 |
| W5 | 文档入库治理 | 让上传、切分、入库可追溯 | 去重、版本、失败重试、审计 | 文档处理链路可追踪、可重放 |
| W6 | 检索质量工程 | 优化召回与回答质量 | 评估集、召回指标、Milvus 参数调优 | 指标可量化，质量可回归 |
| W7 | 会话记忆与链路留痕 | 支持复盘与问题定位 | 会话追踪、历史留存、回放能力 | 能按用户/会话回看完整链路 |
| W8 | API 契约与错误体系 | 统一开发体验 | 返回结构、错误码、参数校验、OpenAPI | 前后端联调成本下降 |
| W9 | CI/CD 与发布门禁 | 实现可重复发布 | 构建流水线、制品版本、发布检查清单 | 一键构建/部署/回滚可执行 |
| W10 | 备份恢复与容灾 | 提升可恢复性 | MySQL/Redis/Milvus 备份与恢复方案 | 可完成演练并恢复数据 |
| W11 | 压测与容量规划 | 找到性能边界 | 压测报告、容量基线、资源建议 | 知道系统极限和瓶颈 |
| W12 | 运营化收尾 | 形成持续运行机制 | Runbook、SOP、验收结论 | 项目可交接、可运维、可持续迭代 |

## 6. 前 8 个 P0 任务的具体改造方法

> 这一节回答“具体要改什么方法 / 模块”，方便直接进入开发。

| ID | 需要改的方法 | 主要改动点 | 涉及模块 / 文件 |
|---|---|---|---|
| P0-1 | 配置加载链路：`application.yaml`、`application-local.yaml`、`@Value` / `@ConfigurationProperties` | 把密钥、数据库、Milvus、Redis、对象存储等敏感项外置；统一环境变量覆盖；新增配置校验 | `src/main/resources/application*.yaml`、配置类 |
| P0-2 | 认证入口：登录接口、鉴权过滤器、拦截器、`SecurityFilterChain`（如已引入） | 给 `ChatController`、上传、管理类接口加统一身份识别；把用户上下文注入到请求链路 | `Controller`、`Config`、`Security` 相关类 |
| P0-3 | 请求链路方法：`OncePerRequestFilter` / `HandlerInterceptor` / AOP 方法、统一日志封装 | 生成并透传 `traceId` / `requestId`；统一日志格式；暴露健康检查和指标 | `Config`、日志工具类、Actuator 配置 |
| P0-4 | 稳定性控制方法：超时、重试、降级、限流、线程池隔离相关方法 | 给外部依赖调用加超时与重试；对上传/检索/生成链路增加限流和熔断；控制并发 | 服务层、网关层、线程池配置 |
| P0-5 | 返回与异常方法：`Result`、全局异常处理器、参数校验注解 | 统一成功/失败返回结构；补全错误码；把业务异常和系统异常分层处理 | `Config/Result`、`Exception`、Controller 入参 |
| P0-6 | RAG 入库链路方法：上传、解析、切分、去重、入库、刷新索引 | 把文档从上传到向量化入库拆成可重试步骤；记录每一步状态；入库后显式刷新 | 上传服务、解析服务、切分服务、`MilvusCollectionService` |
| P0-7 | 审计记录方法：查询、写入、回放、状态更新 | 让每次问答、检索、入库都有审计记录；支持按用户/会话/文档回查 | `TraceRecordService`、审计表、查询接口 |
| P0-8 | 发布和恢复脚本：构建、部署、回滚、备份、恢复方法 | 固化 CI/CD 脚本；建立数据库、Milvus、Redis 的备份恢复步骤；增加发布前检查 | `pom.xml`、脚本目录、运维文档 |

### 6.1 针对 `MilvusCollectionService` 的具体方法优化建议

当前这个类已经比较接近“集合管理中枢”，建议继续强化下面这些方法：

- `add(String collectionName, List<Document> documents)`
  - 增加文档去重、空内容过滤、批量入库失败重试
  - 入库后记录写入结果与失败原因
- `ensureReadyForWrite(String collectionName)`
  - 集合不存在时自动创建，但需要增加创建幂等和并发保护
  - 建议在创建后补充健康检查和加载确认
- `ensureReadyForRead(String collectionName)`
  - 从“返回 null”优化为更明确的状态返回，减少调用方误判
  - 可增加加载失败原因和重试提示
- `drop(String collectionName)` / `rebuild(String collectionName)`
  - 增加危险操作确认机制
  - 记录操作人、时间、原因，避免误删
- `resolveCollectionName(String collectionName)`
  - 建议增加集合名白名单规则和合法性校验
- `getVectorStore(String collectionName)` / `createVectorStore(String collectionName)`
  - 把连接参数、数据库名、集合名统一从配置读取并校验
  - 对缓存失效场景补充自动刷新逻辑
- `createCollectionIfAbsent(String collectionName)`
  - 把建表字段定义抽成独立方法，方便未来扩展 schema
  - 对索引创建、加载、刷新做更细粒度的错误记录
- `loadCollection(String collectionName)` / `unloadCollection(String collectionName)`
  - 增加加载状态确认和幂等处理
  - 对失败原因进行标准化输出，方便排障
- `isLoaded(String collectionName)`
  - 将状态判断结果统一封装成明确状态对象，避免只靠布尔值判断
  - 增加缓存与真实状态一致性的校验
- `flush(String collectionName)`
  - 建议在批量入库完成后统一调用，并记录刷盘结果
- `createEmbeddingIndexIfAbsent(String collectionName)`
  - 把索引类型、度量方式、参数抽成配置模板，便于调优和压测

## 7. 推荐推进方式

- 以周为单位推进：每周聚焦 1 个主题
- 以日为单位更新：每天收工前只改状态和补充阻塞项
- 以证据为准：任务完成必须有截图、日志、PR、测试结果或文档链接
- 以可回滚为底线：任何上线改动必须可回退

## 8. 里程碑验收建议

- M1：安全基线完成，敏感配置脱离仓库
- M2：鉴权、日志、指标基础完成
- M3：入库与检索治理完成，质量可量化
- M4：交付与恢复能力完成，具备企业级运行条件

## 9. 风险清单

- 敏感配置散落在多个文件中，清理成本高
- 检索质量改善与模型能力强相关，需建立评估集
- 备份恢复演练可能暴露数据结构不一致问题
- 过早拆分架构会带来复杂度，建议先做工程治理
