## 二、CRAG 门控证据分改进（RetrievalQualityGate）

原实现：`best = max(fused score)`，单块侥幸高分即可过闸。  
新实现：**证据分 = top × 支撑度系数**，系数 = `0.7 + 0.3 × min(1, 支撑块数/3)`，  
支撑块 = 融合分 ≥ 0.3 的候选。证据既要有高度也要有广度：

- 知识问答（如"Kafka 设计了哪些 Topic"）→ 首轮 evidence≥0.45 直接通过（实测验证）
- 无关问题（如"我的项目叫什么"）→ evidence=0 → 重检索 → 仍不足 → 记忆个性化分支

## 四、瓶颈定位过程（供复现）

1. 4000 并发首测：客户端 0 错误但服务端 7900 次 `Neo4j Connection pool pending acquisition queue is full`  
   → 定位到实体识别每请求查图库 → 实体缓存 + 池扩容后归零。
2. 检索步 p95 尖刺（p50 27ms / p95 2.2s）→ rerank 远程调用限速 → 结果缓存。
3. 分步探针（scripts/step_probe.py）：entity/rewrite/memory 均 ~0ms，瓶颈收敛于 retrieval 步内部  
   （Milvus 搜索 + Redis + Kafka 异步），尾延迟与虚拟线程 carrier 调度相关。

## 五、水平扩展路径（单机 → 上万 QPS）

- 无状态后端多实例 + LB（Redis/Milvus/Kafka/MySQL 共享），吞吐线性扩展
- Dashscope rerank/embedding 为外部限速依赖：重排缓存已加，量大时可切换私有部署 rerank 模型
- Kafka analytics-event 消费端积压重试错误需接通 AnalyticsConsumer（企业级矩阵 P0-3）
